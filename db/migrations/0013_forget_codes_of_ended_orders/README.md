**Why:** a de-registration's security codes are needed only to file it, and an order that has ended (completed, failed for good, cancelled) is never filed again, so the domain now drops them when an order ends (`applyEvent`, launch plan Q22, provisional), as it already dropped a Neuzulassung's bank account.
**Breaks without it:** the adapter writes `encrypted_security_codes = NULL` for an ended de-registration, which 0010's check refuses, so no de-registration could be completed, failed or cancelled.
**Live table:** safe. It swaps one check for a looser one that every existing row satisfies, and changes no data: orders that ended before this migration keep their codes until a separate purge removes them. **Rolling the app back** past this release is not safe for data written after it: the previous release decrypts `encrypted_security_codes` unconditionally, so every de-registration that ended under this release fails to load there (its status page, "resend my link"). Roll forward instead. **The `down.sql` is destructive:** it deletes every de-registration that has forgotten its codes (with its payment, history and token), because 0010's check cannot hold one; it runs in dev and CI only, where those orders are the seed's and `db:seed` loads them again.
