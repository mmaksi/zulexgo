**Why:** a Neuzulassung order waits for the customer's verified identity before anything is filed (plan N5). Ending that wait needs two more kinds of failure (a verification that failed, and a verified person who is not the owner on the order) and a place to remember that the reminder was sent, so the customer is reminded once however often the poller visits. The provider's verification id may be part of the customer's start link, so it is now held encrypted like a status token.
**Breaks without it:** an order cannot store the new failure kinds (the check refuses them), the reminder would be sent on every visit, and the adapter, which now decrypts the verification id, cannot read a plaintext one.
**Live table:** safe. It widens a check, adds a column with a default, and clears the verification id of rows that hold one, which today are only the seed's on dev and staging (Neuzulassung is not on sale, so no real order has one). Those seeded orders (`ZG-SEED13` and `ZG-SEED14`, the Neuzulassung at statuses 2 and 3) keep their status but lose the verification until they are deleted and the seed is loaded again, since the seed leaves an existing order as it is; none is polled, so nothing reads the missing one. Ciphertext carries no marker, so the clearing cannot tell a plaintext id from an encrypted one: reapplying the migration after a `down` in dev clears the ids again. The `down.sql` forgets a failure of the new kinds.
