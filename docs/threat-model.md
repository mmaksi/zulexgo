# ZulexGO — Threat model

Written for N8 of [registration-plan.md](registration-plan.md), from the code as merged on 2026-10-05. It holds facts: each control names the file or test that backs it, and what it leaves open is said plainly. It is the Neuzulassung addendum; the de-registration threat model that launch-plan M7 asks for is not written, so the controls both services share are listed first, once.

A Neuzulassung holds far more than a de-registration: a name, birth date and place, an address, a phone number, an IBAN, an eVB number and the Teil II code, where a de-registration holds a plate, a VIN and three security codes.

## What both services already have

| Control | Where | Backed by |
|---|---|---|
| The status link is the order's only credential: 256 random bits, kept as a SHA-256 hash for lookup and an AES-GCM copy bound to the order; a new link replaces the old | `crypto-token-generator.ts`, `postgres-application-repository.ts` | token generator and repository contract suites |
| A status page, a document download, a cancel or correction, and a resend of the link are counted per address (60 a minute, 20 a minute, 10 an hour, 5 an hour; a resend 3 an hour per order too), before anything is read | `RATE_LIMITS`, `app/status/` | `lookup.test.ts`, `order-change.test.ts`, `request.test.ts`, `document-download.test.ts` |
| An unknown link, a wrong link and an order that cannot be cancelled get one answer each, so none tells which orders exist | `lookup.ts`, `order-change.ts`, `resend-status-link.ts` | the same tests |
| The Stripe webhook and the identity callback refuse an unsigned or forged body with a 400. The identity callback carries no outcome: the result is read from the provider, so a replayed or repeated callback only repeats a read | `app/api/webhooks/` | `handle.ts` tests, `identity-verification.test.ts` |
| A secret (security codes, and a Neuzulassung's owner data, bank account, eVB number, Teil II code) prints as a placeholder however it is turned into text, and only an adapter reveals it; lint refuses `.reveal()` in `app/**` and `src/ui/**`; failures are logged by name only | `secret.ts`, `eslint.config.mjs`, `failed-because.ts` | `secrets-absent-from-logs.test.ts`, `client-bundle-secrets.test.ts`, `status-page-secrets.test.ts` |
| Production refuses to boot on the fake identity check while a service that verifies is on sale | `fakeIdentityProblem` in `env.ts` | `env.test.ts` |

## Neuzulassung

| Threat | What stops it | What it leaves |
|---|---|---|
| **A car is registered in someone else's name:** the attacker types the victim's name and birth date | Nothing is filed before the identity check (status 3). The person verified must be the owner on the order: names are compared whole, ignoring case, accents and spellings, the birth date exactly (`isTheOwner`). A mismatch ends at 5b with nothing filed | Only as strong as the identity provider. Today only the fake adapter exists; production refuses it while Neuzulassung is on sale, so the service cannot launch on it |
| **A stolen Teil II and its code:** a thief with the papers registers the car in their own name, verifying as themselves | Nothing of ours. The identity check proves who the keeper is, not that the car is theirs. The eVB number, the Teil II and its code are what the API requires and the authority's own checks accept; we do not verify them | Accepted. ZulexGO cannot tell a thief holding the papers from their owner. Whether Zulex or the authority adds a check is Q56; a verified identity does leave a named person behind each order |
| **The owner's name is swapped to the person who verified:** an order with a mismatch is corrected at 5b to the verifier's name | Name and birth date can be corrected only while the order's identity was never verified, and the correction runs the same check again, so the order ends with the person who verified (`correct-application.ts`) | The same as the line above: the check ties the order to a person, not to the car |
| **A stranger's bank account:** the IBAN is typed in the funnel and the vehicle tax is collected from it by direct debit | The funnel and the domain accept German IBANs with a valid checksum only (`bank-account.ts`). The power of attorney at checkout also carries the direct-debit mandate (Q46, a draft text) | Nothing checks that the account is the keeper's, and Zulex's `sepaInfo` has no account-holder field (Q56). A keeper could enter an account that is not theirs. For the lawyer and the founder (Q46, Q54) |
| **Personal data behind a leaked status link** | The status page shows the reference, the status and its steps, the last four characters of the VIN, our wording of a failure, the amounts of a refund and the list of documents; never the owner, the address, the IBAN, the eVB number or the Teil II (`status-page-secrets.test.ts`). No email template has a field for the owner's data (`EmailTemplate` in `mailer.ts`) | A link holder can download the order's documents. They are the authority's PDFs (confirmation, temporary certificate, fee statement) and their contents have not been seen: the Zulex spike (N4) is not done. A keeper's name and address are likely in them. The link does not expire (Q22) |
| **Personal data at rest:** a database dump or a leaked backup | The owner, address, phone, bank account, eVB number and Teil II code are one AES-GCM blob bound to the order's reference, the provider's verification id and the status token are encrypted, and a blob copied onto another order does not decrypt (`postgres-application-repository.test.ts`). The bank account is not stored once the order has ended (`applyEvent`, `new-registration-retention.test.ts`) | One key (`CODES_ENCRYPTION_KEY`) with no rotation. An order abandoned at checkout keeps the whole blob, its IBAN included, for as long as nothing deletes it (Q22). The VIN, the email, the status and its history are plain columns |
| **Flooding the postcode check or the checkout:** cost at Zulex and the payment provider, orders and payments nobody pays, and probing the duplicate warning (Q38) with guessed VINs | The postcode check is limited to 30 an hour and the checkout to 10 an hour per address, counted before anything is read or opened, every attempt counting, invalid ones too (`requests.ts`, `requests.test.ts`) | The limit is per address, so an attacker with many addresses is not bounded and customers behind one shared address (a carrier's) share one allowance. There is no other bot defence. De-registration's funnel is not limited yet (M7) |
| **Guessing an invite code, or ordering a service in beta without one** (N9) | The code is checked on the server, twice: when it is redeemed (10 attempts an hour per address, every attempt counted, right ones too, and a limiter that cannot answer refuses) and again by `submitCheckout` on every order, so a crafted checkout without a cookie, or with a revoked code, is refused (`InviteRequired`). Codes are secrets in the environment, at least 8 characters, never in an error or a log; the cookie is HttpOnly, SameSite=Lax and secure outside dev. A daily number of checkouts per service bounds what a leaked code can do (`BetaFull`) | Codes are compared as text, not in constant time, behind the attempt limit. A code works for whoever holds it: it identifies a person only by the one you gave it to, and revoking one means deleting it and redeploying. The cap counts places taken, not orders paid, so abandoned checkouts use up places |
| **The monitoring report read by a stranger, or carrying a customer** (N9) | `GET /api/internal/report` answers only to the cron secret as a bearer token, compared in constant time, and refuses everyone while none is set; it is never cached. It reads each order's status, history and verification deadline and nothing else (`findTrailsSince`), so the Postgres adapter decrypts nothing and the answer holds counts only (`order-report.test.ts`, `handle.test.ts`) | The cron secret is the poller's too: whoever holds it can also trigger a poll. A leaked secret shows how many orders there are and where they stand, not who they are |
| **A response or error that quotes the customer:** Zulex echoes the owner's data, IBAN, eVB number and Teil II code | The adapter never logs a response body and logs failures by name only | The same for any future adapter: the first Zulex run will show what the real responses carry |
